# Customer Service Agent System

A Python/FastAPI customer-service assistant that routes a customer message through triage, a deterministic resolution workflow, and human escalation when needed. It combines LLM-powered language understanding with code-controlled workflows so the model can communicate naturally without deciding business actions or policy branches.

## What it does

- Classifies incoming requests into a customer-service `flow` and `subflow`.
- Loads the matching workflow from `src/data/sequence_table_autogenerated.json`.
- Collects customer details, calls backend functions, evaluates deterministic checks, and sends natural customer-facing responses.
- Separates empathetic acknowledgements from the next required resolution step, allowing the UI to show them as separate chat bubbles.
- Escalates failed or unsupported workflows with a structured handoff payload.
- Exposes a browser-ready FastAPI chat endpoint with CORS support and terminal lifecycle logging.
- Supports voice messages: browser microphone audio is transcribed to text before entering the normal chat flow.

## Architecture

```text
Frontend
  │ POST /api/v1/chat
  ▼
FastAPI API
  ▼
Orchestrator
  ├─ TriageAgent       → chooses flow + subflow
  ├─ SequenceLoader    → loads the matching workflow from JSON
  ├─ ASR Service       → transcribes microphone audio with Groq Whisper
  ├─ ResolutionAgent   → executes the current workflow step deterministically
  │    └─ BackendFunctionRegistry → calls backend functions
  └─ EscalationAgent   → prepares a structured human handoff on failure
```

### Agent responsibilities

| Component | Responsibility |
| --- | --- |
| `TriageAgent` | Uses the LLM to identify the customer’s request, flow, and subflow. |
| `ResolutionAgent` | Walks a `StepSequence`, extracts one customer slot at a time, calls functions, evaluates checks, and phrases customer messages. |
| `EscalationAgent` | Creates an escalation payload with reason, priority, attempted steps, ticket state, and a customer-safe message. |
| `Orchestrator` | Owns active ticket state and connects triage, resolution, and escalation for each chat turn. |

## Workflow data

All workflows live in one file:

`src/data/sequence_table_autogenerated.json`

The loader supports two row formats in that file:

1. **Autogenerated rows** with `steps` as a list. These are converted into a safe linear workflow and are useful as a draft.
2. **Detailed rows** with `steps` as an object. These define real slot sources, backend functions, checks, branches, and responses. Use this format for production-ready flows.

For example, the detailed `Order Issue / Manage Cancel` flow asks for an account and order ID, derives shipping status, branches on `not_shipped`, and then either cancels the order or follows the membership/refund path.

### Step types

- `slot`: Collects customer-provided data or derives a value with a backend function.
- `action`: Executes a backend operation.
- `check`: Branches with deterministic operators such as `equals`, `in`, `is_true`, and `less_than`.
- `response`: Sends a customer-facing message and optionally ends the sequence.

The LLM never decides a check result or which action to execute. It only extracts a requested customer value and phrases the response naturally.

## Backend functions

`src/agents/resolution_functions.py` contains one async placeholder function per supported operation, such as `shipping_status`, `verify_identity`, `update_order`, `offer_refund`, `membership_privileges`, and `notify_internal_team`.

Replace these placeholders with database, payment, order-management, notification, or knowledge-base integrations. Functions used by a `check` should return simple, predictable values:

```python
async def shipping_status(slots: dict[str, Any]) -> str:
    # Look up slots["order_id"] in an order service.
    return "shipped"  # or "not_shipped"
```

## API

Start the server from the repository root:

```bash
uvicorn src.main:app --reload
```

### Health check

```http
GET /api/v1/health
```

### Chat

```http
POST /api/v1/chat
Content-Type: application/json

{
  "query": "I want to cancel my order",
  "session_id": null
}
```

The endpoint also accepts `message` instead of `query`, and `user_id` instead of `session_id`.

Example response:

```json
{
  "message": "I’m sorry this has been frustrating.\n\nCould you share your order number?",
  "messages": [
    "I’m truly sorry this has been frustrating.",
    "To help resolve this, could you share your order number?"
  ],
  "ticket_id": "...",
  "session_id": "...",
  "finished": false
}
```

Store and send back `session_id` on later requests so the in-memory workflow can continue. The frontend should render each entry in `messages` as its own bot message.

### Speech-to-text

```http
POST /api/v1/asr/transcribe
Content-Type: multipart/form-data
```

Send an `audio` field containing a browser-recorded audio file. The endpoint returns:

```json
{ "text": "I want to cancel my order" }
```

The bundled frontend microphone button records WebM audio, transcribes it, and automatically sends the resulting text to `/api/v1/chat`.

## Configuration

Copy `.env.example` to `.env` at the repository root and configure a provider:

```env
GENERATION_BACKEND=groq
GROQ_API_KEY=your_key_here
GENERATION_MODEL=openai/gpt-oss-120b

# The frontend origin, not the backend URL. Do not include a trailing slash.
CORS_ALLOW_ORIGINS=http://localhost:5173
LOG_LEVEL=INFO
```

Supported providers are Groq, Gemini, and Cohere. `GENERATION_MODEL` is optional; the API selects a provider-specific default when it is not set.

For a locally double-clicked HTML file (`file://`), the browser origin is generally `null`:

```env
CORS_ALLOW_ORIGINS=null
```

Serving the frontend from a local HTTP server is preferred.

## Monitoring and logs

The application logs the full workflow lifecycle to the terminal at `INFO` level: customer messages and session IDs, triage results, selected workflows, ticket snapshots, extracted/derived slots, backend function inputs and outputs, checks, branches, and escalation reasons.

These logs may contain customer names, account IDs, or order IDs. Keep this detail for local development only; mask sensitive fields and send logs to a protected observability service before production deployment.

## Current limitations and next steps

- Backend functions are placeholders; connect them to real services before using the project with real customer data.
- Active tickets are stored in memory. Add a database or cache for restarts and multi-instance deployments.
- Detailed JSON workflows must be completed for every production flow. Autogenerated rows do not contain reliable branch logic.
- Human approval currently ends the ticket rather than supporting an approve-and-resume workflow.
- Add authentication, rate limiting, input guardrails, PII redaction, and persistent audit logging before production use.
